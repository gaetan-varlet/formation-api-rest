# Le streaming

----

## Le problème du modèle classique (`List<T>`)

Pourquoi `findAll()` sature la JVM sur les gros volumes

```java
// Modèle bloquant classique
@GetMapping
public List<Vin> findAll() {
    return vinRepository.findAll();
}
```

- **Mémoire en O(N)** : Les milliers de lignes SQL sont instanciées simultanément sous forme d'entités JPA sur le tas (Heap), puis dupliquées lors de la conversion JSON avant l'envoi réseau
- **Risque majeur** : Pics de charge mémoire non bornés, cycles violents du ramasse-miettes, et risque d'OutOfMemoryError: Java heap space
- **Latence (TTFB dégradé)** : Le client HTTP ne reçoit pas le moindre octet tant que l'ensemble du jeu de données n'est pas entièrement chargé et sérialisé en mémoire

----

## Architecture du streaming bout-en-bout

### Principe : Empreinte mémoire constante en O(1)

Au lieu de charger une collection en RAM, les données circulent dans un tuyau continu :

> PostgreSQL (Curseur JDBC) ==> Stream JPA ==> Jackson (Sérialisation) ==> Socket HTTP

- **Unité de traitement** : Chaque enregistrement est lu, sérialisé directement vers le flux réseau (OutputStream), puis devient immédiatement éligible au Garbage Collector
- **Consommation mémoire** : Constante, que la table contienne 10 lignes ou 2 millions de lignes
- **Délai initial (TTFB) :** Immédiat ; les premiers octets partent vers le client dès la première ligne lue

## Étape 1 — Le Repository Spring Data

Déclarer un retour `Stream<T>`

```java
public interface VinRepositorySpringData extends JpaRepository<Vin, Integer> {

@QueryHints(value = {
    // OBLIGATOIRE PostgreSQL : évite de charger les 500k lignes d'un coup en RAM JVM
    @QueryHint(name = HibernateHints.HINT_FETCH_SIZE, value = "2000"),
    // DÉFENSE EN PROFONDEUR : désactive les snapshots de dirty checking
    @QueryHint(name = HibernateHints.HINT_READ_ONLY, value = "true")
})
Stream<Vin> streamAllBy();

}
```

- **Le piège PostgreSQL (fetch_size)** : Par défaut, le driver jdbc a un fetchSize = 0, il télécharge l'intégralité du résultat en mémoire vive avant de rendre la main. Définir un lot (ex. 2000) active le vrai curseur côté base
- **Rôle de HINT_READ_ONLY** : Déjà pris en charge au niveau global par `@Transactional(readOnly = true)`, mais le déclarer ici garantit la sécurité si la méthode est appelée dans une transaction parente mal configurée

## Étape 2 — Le Service (Transaction & Sérialisation)

Consommer le flux et écrire au fil de l'eau

```java
@Service
@RequiredArgsConstructor
public class VinService {
    private final VinRepositorySpringData vinRepository;
    private final ObjectMapper objectMapper;
    @Transactional(readOnly = true) // Transaction active obligatoire pour maintenir le curseur JDBC ouvert
    public void streamVinsAsJson(OutputStream outputStream) throws IOException {
        // try-with-resources obligatoire : libère le curseur DB et la connexion du pool
        try (Stream<Vin> vinStream = vinRepository.streamAllBy();
             SequenceWriter seqWriter = objectMapper.writerFor(Vin.class).writeValuesAsArray(outputStream)) {
            Iterator<Vin> iterator = vinStream.iterator();
            while (iterator.hasNext()) {
                seqWriter.write(iterator.next()); // Sérialisation unitaire vers la socket HTTP
            }
        }
    }
}
```

- **Durée de transaction** : La transaction reste ouverte pendant toute l'écriture du stream. Ne jamais faire sortir le `Stream<Vin>` de la méthode du service
- **Gestion mémoire avec SequenceWriter** : Jackson ouvre automatiquement le tableau (`[`), sépare chaque objet par une virgule, et ferme le tableau (`]`) à la clôture du writer

## Étape 3 — Le Contrôleur Spring MVC

Délégation asynchrone via StreamingResponseBody

```java
@RestController
@RequestMapping("/vins")
@RequiredArgsConstructor
public class VinController {
    private final VinService vinService;

    @GetMapping(value = "/stream", produces = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<StreamingResponseBody> streamVins() {
        // Lambda exécutée de manière asynchrone par Spring MVC
        StreamingResponseBody responseBody = outputStream ->
                vinService.streamVinsAsJson(outputStream);
        return ResponseEntity.ok()
                .contentType(MediaType.APPLICATION_JSON)
                .body(responseBody);
    }
}
```

- **Pourquoi StreamingResponseBody ?** Il fournit un accès direct à l'OutputStream réseau brut de la servlet sans passer par les convertisseurs MVC classiques qui allouent des buffers en RAM
- **Libération des threads** : Le thread initial de traitement de la requête HTTP est libéré immédiatement ; l'écriture du stream s'exécute sur un thread dédié

## Synthèse (1)

| Critère | Approche classique (`List<T>`) | Approche Streaming (`Stream<T>`) |
| :--- | :--- | :--- |
| **Empreinte mémoire (Heap)** | **O(N)** proportionnelle au volume | **O(1) constante (quelques Ko)** |
| **Latence (TTFB)** | Dégradée (attend la fin de la requête) | **Instantanée dès la 1ère ligne** |
| **Connexion DB (HikariCP)** | Empruntée brièvement | **Empruntée pendant tout l'envoi réseau** |

----

## Synthèse (2)

Les 3 règles critiques à connaitre

- **Toujours borner le fetch size JDBC** : Sans fetchSize > 0 sur PostgreSQL, le pilote ramène l'intégralité du résultat en mémoire avant le premier next() (configurable globalement via property : `spring.jpa.properties.hibernate.jdbc.fetch_size: 2000`)
- **Ne jamais faire fuiter un Stream hors du `@Transactional`** : Tenter d'itérer sur le flux dans le contrôleur lève une TransactionRequiredException ou une fermeture de curseur
- **Entités managées vs DTO (select new)** : Pour des volumes massifs (> 100 000 lignes), préférer la projection vers un record / DTO plutôt qu'une entité JPA. Même en lecture seule, accumuler des entités dans la Session Hibernate finit par faire grossir le contexte de persistance
