# Benchmark & Stratégies d'extraction de données

----

## 1. Matrice comparative

| Approche | RAM | Vitesse | Code | Cas d'usage type |
| :--- | :--- | :--- | :--- | :--- |
| **JPA Entités** | $O(N)$ | 🐌 Lent | ⭐ | CRUD unitaire, pagination (< 1 000) |
| **JPA DTOs** | $O(N)$ | 🚗 Moyen | ⭐⭐ | Lecture seule synchrone (< 20 000) |
| **JPA Stream** | $O(1)$ | ⚡ Rapide | ⭐⭐⭐⭐ | Flux continu + calculs Java |
| **JDBC Stream** | $O(1)$ | 🚀 Max | ⭐⭐ | Exports massifs bruts (CSV/JSON) |

----

## 2. Pourquoi JPA Stream est plus exigeant qu'il n'y paraît

Écrire `Stream<Vin>` est simple, mais impose 3 contraintes d'infrastructure en production :

1. **Saturation du cache L1 :** par défaut, Hibernate stocke chaque entité lue en mémoire $\rightarrow$ risque d'`OutOfMemoryError`.
2. **Curseur PostgreSQL (`fetchSize`) :** Par défaut à 0 (charge tout en RAM), nécessite le hint `HINT_FETCH_SIZE = 2000`.
3. **Rétention de connexion :** La transaction et la connexion HikariCP restent bloquées tout le long du transfert réseau.

> **Remède :** Projeter vers un Record/DTO (`SELECT new ...`) pour désactiver le cache Hibernate.

----

## 3. Quand JPA Stream reste pertinent ?

### 1. Réutiliser la logique Java de l'entité

`JdbcClient` extrait du SQL brut. JPA charge l'objet complet avec ses méthodes calculées :

```java
// Réutilisation directe sans recalcul manuel
csvWriter.writeNext(new String[] { vin.getNom(), String.valueOf(vin.getPrixTTC()) });
```

### 2. Zéro plomberie SQL

Déclaration directe dans l'interface Spring Data, sans créer de DAO JDBC séparé :

```java
Stream<Vin> streamAllBy();
```

----

## 4. L'alternative radicale : le Streaming JdbcClient

Pour un export en lecture seule (CSV, JSON), contourner l'ORM simplifie le code et élimine les effets de bord de session :

```java
public record VinExportDto(Integer id, String chateau, BigDecimal prix) {}

@Repository
@RequiredArgsConstructor
public class VinExportDao {
    private final JdbcClient jdbcClient;

    public void streamAll(Consumer<VinExportDto> consumer) {
        // Zéro cache L1, zéro dirty-checking, mapping direct vers le Record
        try (Stream<VinExportDto> stream = jdbcClient.sql("SELECT id, chateau, prix FROM formation.vin")
                .query(VinExportDto.class)
                .stream()) {
            stream.forEach(consumer);
        }
    }
}
```

- **Débit maximal :** Envoi direct des tuples du curseur JDBC vers le flux réseau.
- **Complexité réduite :** Pas de cycle de vie d'entités, pas de désynchronisation de cache.

----

## 5. Arbre de décision : que choisir en pratique ?

```txt
Quel est le besoin d'extraction ?
 │
 ├── 1. Affichage écran / Pagination standard (< 1 000 lignes)
 │       └── ✅ JPA classique (List<Vin> / Pageable)
 │            → Simple, rapide à coder, impact RAM négligeable.
 │
 ├── 2. Extraction moyenne sans calculs (1 000 à 20 000 lignes)
 │       └── ✅ JPA avec Record / DTO (List<VinDto>)
 │            → Évite la surcharge Hibernate tout en restant synchrone.
 │
 ├── 3. Gros volume avec logique Java / calculs métier (> 20 000 lignes)
 │       └── ✅ JPA Stream (Stream<Vin> + StreamingResponseBody)
 │            → Empreinte RAM stable (O(1)), permet d'appeler vin.getPrixTTC().
 │
 └── 4. Export brut massif sans logique métier (CSV / JSON)
         └── ✅ JdbcClient Stream (.query(VinRecord.class).stream())
              → Vitesse maximale, RAM minimale, sans passer par l'ORM.
```
