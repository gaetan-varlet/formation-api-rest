# Benchmark & Stratégies d'extraction de données

----

## 1. Matrice comparative des approches

Comportement constaté sur 100k à 500k lignes :

| Approche | RAM | Débit | Code | Usage cible |
| :--- | :---: | :---: | :---: | :--- |
| **JPA Entités (`List`)** | $O(N)$ | 📉 Chute (GC) | ⭐ | CRUD unitaire (< 1k) |
| **JPA Entités (`Stream`)** | 💥 **OOM** | ❌ Crash | ⭐⭐⭐⭐ | Fausse piste (saturation cache L1) |
| **JPA DTOs (`List`)** | $O(N)$ | 📉 Baisse | ⭐⭐ | Lecture seule synchrone (< 20k) |
| **JPA DTO (`Stream`)** | $O(1)$ | 📈 Stable | ⭐⭐ | Flux pérenne + Spring Data |
| **JDBC Stream (`JdbcClient`)** | $O(1)$ | 🚀 Max | ⭐⭐ | Export brut massif CSV/JSON |

> **Le piège du Stream d'entités :** Hibernate stocke chaque entité lue en session. Sans purge manuelle, le cache L1 sature la RAM. La projection DTO (`SELECT new`) ou JDBC est obligatoire.

----

## 2. Les 3 règles critiques d'infrastructure

1. **`@Transactional(readOnly = true)` obligatoire (JPA & JDBC) :**
   - Sans transaction active, PostgreSQL est en `autoCommit = true`.
   - Dans ce mode, le driver PostgreSQL **ignore totalement le streaming** et charge tout en RAM JVM.
2. **Dimensionner le `fetchSize` (1 000 à 2 000) :**
   - Compromis optimal latence/débit (blocs réseau de 200 à 300 Ko). Au-delà, gain marginal (< 3 %) et surcoût mémoire inutile.
3. **Tampon Jackson et gestion du `flush()` :**
   - `writer.write()` sérialise dans un buffer mémoire local (~8 Ko), pas directement sur la carte réseau.
   - ⚠️ **Ne jamais flusher dans la boucle :** un `flush()` unitaire forcerait l'envoi de micro-paquets TCP. On flashe **une seule fois** à la fin.

----

## 3. Implémentation : JPA DTO Stream

Projection directe vers un Record pour contourner le cache L1 Hibernate :

```java
@Transactional(readOnly = true)
public void streamJpa(OutputStream os) throws IOException {
    try (SequenceWriter writer = objectMapper.writerFor(VinResponse.class).writeValuesAsArray(os);
         Stream<VinResponse> stream = repository.streamDtos()) {

        Iterator<VinResponse> iterator = stream.iterator();
        while (iterator.hasNext()) {
            writer.write(iterator.next());
        }
        writer.flush(); // Envoi final du reliquat du buffer
    }
}
```

- **Avantage :** Maintient l'interface Spring Data sans charger d'entité managée.

----

## 3 bis. Implémentation : JDBC Stream (JdbcClient)

Accès direct via `spring-jdbc`, **100 % indépendant de JPA/Hibernate** :

```java
@Transactional(readOnly = true)
public void streamJdbc(OutputStream os) throws IOException {
    try (SequenceWriter writer = objectMapper.writerFor(VinResponse.class).writeValuesAsArray(os);
         Stream<VinResponse> stream = jdbcClient.sql("SELECT id, chateau, prix FROM formation.vin")
                 .query(VinResponse.class)
                 .stream()) {

        Iterator<VinResponse> iterator = stream.iterator();
        while (iterator.hasNext()) {
            writer.write(iterator.next());
        }
        writer.flush();
    }
}
```

- **Indépendance totale ORM :** Ignore les annotations `@Entity`, n'ouvre aucun `EntityManager` et ne fait aucun dirty-checking. Mappe directement en Record au fil de l'eau.

## 4. Synthèse des bonnes pratiques d'extraction

```txt
Quel est l'objectif ?
 │
 ├── 1. Affichage écran / Navigation IHM
 │       ├── Petit volume (< 1 000) ──► ✅ JPA classique (List<T>)
 │       └── Grand volume            ──► ⚠️ Bannir OFFSET / LIMIT
 │                                       ✅ Pagination par curseur (keyset) :
 │                                          WHERE id > :dernierId LIMIT 50
 │
 └── 2. Export de données (CSV / JSON)
         ├── Volume modéré (< 20 000) ──► ✅ JPA Projection DTO synchrone
         ├── Gros volume (Spring Data)──► ✅ JPA DTO Stream + SequenceWriter
         └── Débit maximal brut       ──► ✅ JDBC Stream (JdbcClient)
```
