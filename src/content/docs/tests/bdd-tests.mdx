## H2 en mémoire vs PostgreSQL en test

Par défaut, les tests d'intégration s'appuient sur une base en mémoire **H2** *(voir [Configuration de la BDD](/formation-api-rest/spring-boot/configuration-bdd/))*, qui démarre instantanément sans Docker ni serveur externe.

### Pourquoi l'alternance fonctionne : le rôle d'Hibernate

- **Abstraction du SQL :** Spring Data génère des requêtes abstraites (JPQL / requêtes dérivées).
- **Rôle du dialecte :** Hibernate détecte le driver (`H2` ou `PostgreSQL`) et traduit le JPQL en SQL adapté au moteur sous-jacent :
  - pagination (`LIMIT / OFFSET`) ;
  - fonctions de date et concaténation adaptées au SGBD ;
  - stratégies de génération des clés primaires (`IDENTITY` vs `SEQUENCE`).

### Où s'arrête la magie : quand H2 ne suffit plus

Les écarts entre H2 et PostgreSQL apparaissent dès que l'on sort du SQL généré par JPA :

- **Requêtes SQL natives (`nativeQuery = true`) :** tolérées tant que le SQL reste strictement standard, mais en échec dès qu'on emploie des types ou fonctions propriétaires (`JSONB`, opérateurs ou fonctions PostgreSQL…) ;
- **Comportements SGBD spécifiques :** gestion des clés, contraintes, schémas ou verrouillage.

### Pistes pour limiter les écarts

- **Émulation `MODE=PostgreSQL` dans H2 :** ajuste l'URL JDBC de H2 (`jdbc:h2:mem:testdb;MODE=PostgreSQL`) pour tolérer une partie de la syntaxe PostgreSQL, mais reste une couverture partielle.
- **Zonky Embedded Postgres :** exécute un véritable PostgreSQL embarqué sans nécessiter Docker.
- **Testcontainers (PostgreSQL) :** démarre un conteneur Docker PostgreSQL éphémère pendant les tests, garantissant une parité stricte avec la base de production.

## Règle d'arbitrage

- **Conserver H2 en mémoire** tant que l'accès aux données repose sur du JPA / JPQL standard et que l'on privilégie la rapidité d'exécution.
- **Basculer sur un vrai moteur PostgreSQL en test** (Testcontainers, Zonky Embedded Postgres ou équivalent) dès l'introduction de requêtes SQL natives ou de types spécifiques à PostgreSQL.
