Cette page synthétise les bases du mapping objet-relationnel (**JPA / Hibernate**) utilisées dans les modules précédents et nécessaires avant d'aborder les optimisations de **Spring Data JPA**.

## Annotations de mapping d'une entité

Prenons l'exemple de l'entité `Vin` introduite dans [Configuration de la BDD](/formation-api-rest/spring-boot/configuration-bdd/#création-de-lentité-java-jpa) :

```java title="src/main/java/fr/insee/formationapirest/model/Vin.java"
@Getter
@Setter
@Entity
@Table(name = "vin")
public class Vin {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String chateau;
    private String appellation;
    private Double prix;
}
```

- **`@Entity`** : indique à JPA/Hibernate que la classe correspond à une table en base *(exige un constructeur sans argument, présent automatiquement tant qu'aucun autre constructeur n'est défini)*.
- **`@Table(name = "vin")`** : optionnelle ici — par défaut, JPA associe la classe `Vin` à une table du même nom. Elle sert uniquement si le nom diffère ou pour préciser un `schema`.
- **`@Id`** : désigne la clé primaire (obligatoire sur toute `@Entity`).
- **`@GeneratedValue(strategy = GenerationType.IDENTITY)`** : confie la génération de l'identifiant à la base via la colonne auto-incrémentée.
- **`@Column`** : optionnelle par défaut (Spring Boot mappe chaque champ vers une colonne en *snake_case*, ex. `monChamp` → `mon_champ`). Utile au besoin pour fixer un nom (`name`), une contrainte (`nullable = false`, `unique = true`) ou une longueur (`length = 100`).
- **`@Getter` / `@Setter` (Lombok)** : utilisez ces deux annotations plutôt que **`@Data`** sur une `@Entity`. `@Data` génère `toString()`, `equals()` et `hashCode()` sur **tous** les champs, ce qui cause deux bugs classiques avec Hibernate :
  - **`toString()` :** accède aussi aux relations `LAZY` — un simple log (`log.debug(...)`) ou le débogueur déclenche des `SELECT` cachés, une `LazyInitializationException` hors transaction, ou un `StackOverflowError` sur une relation bidirectionnelle (`Vin` ↔ `Region`). *(Si vous voulez tout de même un `toString()`, utilisez `@ToString(onlyExplicitlyIncluded = true)` avec `@ToString.Include` uniquement sur les champs simples, ou écrivez-le à la main.)*
  - **`equals()` / `hashCode()` :** inclut l'`id`, dont la valeur change quand elle passe de `null` à un identifiant généré au `save()`, ce qui casse la recherche de l'entité dans un `Set` ou une `Map` *(et compare mal les proxies Hibernate)*.

## Clé primaire : stratégie de génération et type Java

| Stratégie (`@GeneratedValue`) | Type Java | Fonctionnement et cas d'usage |
| :--- | :--- | :--- |
| **`IDENTITY`** | `Long` | Délègue à la colonne auto-incrémentée (`GENERATED BY DEFAULT AS IDENTITY`). Simple et adapté aux API CRUD classiques *(un `POST` unitaire ne fait qu'un aller-retour)* ; en revanche, comme la BDD n'attribue l'ID qu'à l'exécution de l'`INSERT`, Hibernate doit envoyer `N` requêtes une par une lors d'un `saveAll()` *(pour des insertions en masse, passez par `SEQUENCE` ou [Batch JDBC](/formation-api-rest/acces-donnees/jdbc-et-batching/#écritures-massives--saveall-vs-batch-jdbc))*. |
| **`SEQUENCE`** | `Long` | Utilise une séquence SQL (`CREATE SEQUENCE`) avec pré-allocation par lots *(ex. `allocationSize = 50` : 1 seul appel récupère 50 IDs en mémoire, puis Hibernate peut grouper les 50 `INSERT` en un seul envoi batch)*. Indispensable pour profiter du *batching* directement avec Hibernate (`saveAll()`). |
| **`UUID`** | `java.util.UUID` | Utilisez **UUIDv7** (`@UuidGenerator(style = UuidGenerator.Style.VERSION_7)` sous Hibernate 7) : ordonné dans le temps, non devinable (`/vin/1`, `/vin/2`…) et **généré côté Java avant l'`INSERT`** (0 aller-retour préalable et compatible *batching*). Compromis face à `Long` : taille doublée (16 octets vs 8) et URLs moins lisibles. |
| **`AUTO`** *(défaut si `strategy` omis)* | Selon le SGBD | Laisse Hibernate choisir la stratégie selon la base : à éviter si vous voulez maîtriser le comportement exact en base. |
| *(aucun `@GeneratedValue`)* | `String` ou `Long` | L'identifiant est fourni manuellement par votre code avant le `save()`. Réservé aux vraies clés naturelles immuables (code pays ISO, code commune, SIRET…). |

> 💡 **Pourquoi `Long` plutôt qu'`Integer` ?** Contrairement à `Integer` (limité à ~2,14 milliards), `Long` évite tout risque de saturation sur les tables volumineuses et suit les conventions Spring Data JPA.

:::caution[Toujours un type objet (`Long`), jamais un primitif (`long`)]
Avant insertion en base, un nouvel objet a un identifiant à `null` (`0L` pour un primitif `long`), ce qui permet à Spring Data JPA de distinguer une création (`INSERT`) d'une mise à jour (`UPDATE`).
:::

### Exemple avec UUIDv7 (Hibernate 7)

Si vous optez pour des identifiants `UUID` (générés côté Java au format UUIDv7 ordonné dans le temps), remplacez `@GeneratedValue` par `@UuidGenerator` :

```java title="Vin.java"
import java.util.UUID;

import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import org.hibernate.annotations.UuidGenerator;

@Getter
@Setter
@Entity
@Table(name = "vin")
public class Vin {

    @Id
    @UuidGenerator(style = UuidGenerator.Style.VERSION_7)
    private UUID id;

    private String chateau;
    private String appellation;
    private Double prix;
}
```

- **Pourquoi `@UuidGenerator` (Hibernate) plutôt que `@GeneratedValue(strategy = GenerationType.UUID)` (JPA) ?** `@UuidGenerator` remplace `@GeneratedValue` : l'API JPA standard ne permet pas encore de demander la v7 (elle génère par défaut un UUIDv4 aléatoire). La génération reste **100 % côté Java** (0 aller-retour BDD, compatible *batching*), au prix d'un simple couplage à Hibernate au lieu de JPA pur.
- **Côté Repository et SQL :** déclarez `JpaRepository<Vin, UUID>` et une colonne `id UUID PRIMARY KEY` dans `schema.sql` (sans `GENERATED BY DEFAULT AS IDENTITY`, puisque Java fournit l'UUID avant l'`INSERT`).

## Génération du schéma (`ddl-auto`)

La propriété `spring.jpa.hibernate.ddl-auto` pilote ce que fait Hibernate au démarrage vis-à-vis des tables en base :

| Valeur | Comportement | Quand l'utiliser ? |
| :--- | :--- | :--- |
| **`none`** | Hibernate ne crée ni ne modifie aucune table | Quand les tables existent déjà en base ou sont créées par un script SQL (`schema.sql`) — **valeur par défaut** sur une base externe (PostgreSQL) |
| **`validate`** | Vérifie au démarrage que les tables et colonnes correspondent aux `@Entity` (sinon l'application refuse de démarrer) | Utile pour vérifier que la base et les entités Java restent alignées *(attention : strict sur les types SQL, ex. `Double` vs `DECIMAL`)* |
| **`update`** | Crée/ajoute les tables et colonnes manquantes d'après les `@Entity` | Prototypage uniquement *(à éviter en prod : ne supprime rien et ne gère pas les renommages/migrations complexes)* |
| **`create`** | Supprime puis recrée les tables au démarrage | Environnement jetable *(efface toutes les données à chaque redémarrage)* |
| **`create-drop`** | Comme `create`, puis supprime les tables à l'arrêt de l'application | **Valeur par défaut sur une base embarquée (H2)** si `ddl-auto` est omis *(d'où l'ajout de `none` dans `application.properties` pour utiliser `schema.sql`)* |

## Utiliser un autre schéma que `public`

Par défaut, les tables de l'application vivent dans le schéma **`public`** (recommandation actuelle sur les versions récentes de PostgreSQL pour une base dédiée à l'application). Si votre projet est branché sur un schéma dédié (ex. `mon_schema`) :

- **Réglage global (recommandé) :** ajoutez `spring.jpa.properties.hibernate.default_schema=mon_schema` dans `application.properties` *(s'applique à toutes les entités sans toucher au code Java)*.
- **Réglage ciblé (multi-schémas) :** précisez `@Table(name = "vin", schema = "mon_schema")` sur l'entité concernée.

:::caution[SQL natif et JDBC : `default_schema` ne s'applique pas]
`spring.jpa.properties.hibernate.default_schema` ne s'applique qu'aux entités JPA/Hibernate. Si vous utilisez un autre schéma que `public`, préfixez explicitement le nom de table (`FROM mon_schema.vin`) dans vos scripts `schema.sql`/`data.sql`, vos requêtes `@Query(nativeQuery = true)` et vos appels `JdbcClient` / `JdbcTemplate`.
:::
