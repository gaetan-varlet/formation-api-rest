Cette page synthétise les bases du mapping objet-relationnel (**JPA / Hibernate**) utilisées dans les modules précédents et nécessaires avant d'aborder les optimisations de **Spring Data JPA**.

## Annotations de mapping d'une entité

Prenons l'exemple de l'entité `Vin` introduite dans [Configuration de la BDD](/formation-api-rest/spring-boot/configuration-bdd/#création-de-lentité-java-jpa) :

```java title="src/main/java/fr/insee/formationapirest/model/Vin.java"
@Getter
@Setter
@Entity
@Table(name = "vin")
public class Vin {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String chateau;
    private String appellation;
    private Double prix;
}
```

- **`@Entity`** : indique à JPA/Hibernate que la classe correspond à une table en base *(exige un constructeur sans argument, présent automatiquement tant qu'aucun autre constructeur n'est défini)*.
- **`@Table(name = "vin")`** : optionnelle ici — par défaut, JPA associe la classe `Vin` à une table du même nom. Elle sert uniquement si le nom diffère ou pour préciser un `schema`.
- **`@Id`** : désigne la clé primaire (obligatoire sur toute `@Entity`).
- **`@GeneratedValue(strategy = GenerationType.IDENTITY)`** : confie la génération de l'identifiant à la base via la colonne auto-incrémentée.
- **`@Column`** : optionnelle par défaut (Spring Boot mappe chaque champ vers une colonne en *snake_case*, ex. `monChamp` → `mon_champ`). Utile au besoin pour fixer un nom (`name`), une contrainte (`nullable = false`, `unique = true`) ou une longueur (`length = 100`).
- **`@Getter` / `@Setter` (Lombok)** : utilisez ces deux annotations plutôt que **`@Data`** sur une `@Entity`. `@Data` génère `toString()`, `equals()` et `hashCode()` sur **tous** les champs, ce qui cause deux bugs classiques avec Hibernate :
  - **`toString()` :** accède aussi aux relations `LAZY` — un simple log (`log.debug(...)`) ou le débogueur déclenche des `SELECT` cachés, une `LazyInitializationException` hors transaction, ou un `StackOverflowError` sur une relation bidirectionnelle (`Vin` ↔ `Region`). *(Si vous voulez tout de même un `toString()`, utilisez `@ToString(onlyExplicitlyIncluded = true)` avec `@ToString.Include` uniquement sur les champs simples, ou écrivez-le à la main.)*
  - **`equals()` / `hashCode()` :** inclut l'`id`, dont la valeur change quand elle passe de `null` à un identifiant généré au `save()`, ce qui casse la recherche de l'entité dans un `Set` ou une `Map` *(et compare mal les proxies Hibernate)*.

## Clé primaire : stratégie de génération et type Java

| Stratégie (`@GeneratedValue`) | Type Java | Fonctionnement et cas d'usage |
| :--- | :--- | :--- |
| **`IDENTITY`** | `Long` | Délègue à la colonne auto-incrémentée (`GENERATED BY DEFAULT AS IDENTITY`). Simple et adapté aux API CRUD classiques *(un `POST` unitaire ne fait qu'un aller-retour)* ; en revanche, comme la BDD n'attribue l'ID qu'à l'exécution de l'`INSERT`, Hibernate doit envoyer `N` requêtes une par une lors d'un `saveAll()` *(pour des insertions en masse, passez par `SEQUENCE` ou [Batch JDBC](/formation-api-rest/acces-donnees/jdbc-et-batching/#écritures-massives--saveall-vs-batch-jdbc))*. |
| **`SEQUENCE`** | `Long` | Utilise une séquence SQL (`CREATE SEQUENCE`) avec pré-allocation par lots *(ex. `allocationSize = 50` : 1 seul appel récupère 50 IDs en mémoire, puis Hibernate peut grouper les 50 `INSERT` en un seul envoi batch)*. Indispensable pour profiter du *batching* directement avec Hibernate (`saveAll()`). |
| **`UUID`** | `java.util.UUID` | Utilisez **UUIDv7** (`@UuidGenerator(style = UuidGenerator.Style.VERSION_7)` sous Hibernate 7) : ordonné dans le temps, non devinable (`/vins/1`, `/vins/2`…) et **généré côté Java avant l'`INSERT`** (0 aller-retour préalable et compatible *batching*). Compromis face à `Long` : taille doublée (16 octets vs 8) et URLs moins lisibles. |
| **`AUTO`** *(défaut si `strategy` omis)* | Selon le SGBD | Laisse Hibernate choisir la stratégie selon la base : à éviter si vous voulez maîtriser le comportement exact en base. |
| *(aucun `@GeneratedValue`)* | `String` ou `Long` | L'identifiant est fourni manuellement par votre code avant le `save()`. Réservé aux vraies clés naturelles immuables (code pays ISO, code commune, SIRET…). |

> 💡 **Pourquoi `Long` plutôt qu'`Integer` ?** Contrairement à `Integer` (limité à ~2,14 milliards), `Long` évite tout risque de saturation sur les tables volumineuses et suit les conventions Spring Data JPA.

:::caution[Toujours un type objet (`Long`), jamais un primitif (`long`)]
Avant insertion en base, un nouvel objet a un identifiant à `null` (`0L` pour un primitif `long`), ce qui permet à Spring Data JPA de distinguer une création (`INSERT`) d'une mise à jour (`UPDATE`).
:::

### Exemple avec UUIDv7 (Hibernate 7)

Si vous optez pour des identifiants `UUID` (générés côté Java au format UUIDv7 ordonné dans le temps), remplacez `@GeneratedValue` par `@UuidGenerator` :

```java title="Vin.java"
import java.util.UUID;

import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import org.hibernate.annotations.UuidGenerator;

@Getter
@Setter
@Entity
@Table(name = "vin")
public class Vin {

    @Id
    @UuidGenerator(style = UuidGenerator.Style.VERSION_7)
    private UUID id;

    private String chateau;
    private String appellation;
    private Double prix;
}
```

- **Pourquoi `@UuidGenerator` (Hibernate) plutôt que `@GeneratedValue(strategy = GenerationType.UUID)` (JPA) ?** `@UuidGenerator` remplace `@GeneratedValue` : l'API JPA standard ne permet pas encore de demander la v7 (elle génère par défaut un UUIDv4 aléatoire). La génération reste **100 % côté Java** (0 aller-retour BDD, compatible *batching*), au prix d'un simple couplage à Hibernate au lieu de JPA pur.
- **Côté Repository et SQL :** déclarez `JpaRepository<Vin, UUID>` et une colonne `id UUID PRIMARY KEY` dans `schema.sql` (sans `GENERATED BY DEFAULT AS IDENTITY`, puisque Java fournit l'UUID avant l'`INSERT`).

## Types numériques et montants (`Double` vs `BigDecimal`)

Dans ce cours, `Vin.prix` utilise **`Double`** pour garder des exemples simples. En production, pour tout **montant financier** (prix, TVA, facturation), privilégiez **`BigDecimal`** associé à une colonne SQL **`NUMERIC`**.

### Pourquoi `Double` ne convient pas aux montants

Tout comme `1/3` donne une suite infinie (`0,333333…`) dans notre système décimal (**base 10**), les nombres comme `0.1`, `0.2` ou `19.99` donnent une suite binaire infinie en **base 2** (`Double` / `Float`), que l'ordinateur doit couper et arrondir.

- **Résultat 100 % systématique :** sur n'importe quelle machine, `0.1 + 0.2` en `double` vaut toujours `0.30000000000000004` (et `0.1 + 0.2 == 0.3` vaut `false`). Java masque ce micro-écart à l'affichage d'une valeur seule, mais il apparaît dès qu'on **additionne, multiplie ou compare** des montants.
- **`BigDecimal`** stocke au contraire les chiffres en **base 10** (`1999` avec 2 décimales pour `19.99`), ce qui garantit des calculs exacts. *(Son équivalent entier, **`BigInteger`**, sert uniquement aux entiers dépassant `Long.MAX_VALUE` — cryptographie, très grands compteurs — et reste rarement nécessaire en API REST.)*

### Avantages, inconvénients et pièges

| Critère | `BigDecimal` | `Double` |
| :--- | :--- | :--- |
| **Précision** | Exacte en base 10, contrôle de l'arrondi (`RoundingMode.HALF_UP`) | Approximative en base 2 (inadaptée à l'argent) |
| **Syntaxe** | Verbeuse (`a.add(b)`, `a.multiply(b)`), objets immuables | Opérateurs natifs (`+`, `*`, `<`) |
| **Mémoire (Java)** | **~2,5× à 5× plus lourd** que `Double`/`double` *(+ un nouvel objet alloué à chaque opération)* | Référence *(léger)* |
| **Vitesse CPU** | **10× à 100× plus lent** en calcul pur, mais noyé dans l'I/O (BDD, réseau, disque) sur une API ou un batch de quelques centaines de milliers de lignes *(quelques ms sur le temps total)* ; sensible uniquement en calcul intensif purement CPU sans I/O | Référence *(calcul matériel)* |

:::caution[Les 3 pièges classiques avec `BigDecimal`]
1. **Constructeur :** passez une chaîne ou `valueOf` — `new BigDecimal("0.1")` ou `BigDecimal.valueOf(0.1)` — **jamais** `new BigDecimal(0.1)` (qui capture déjà l'imprécision binaire du `double`).
2. **Comparaison :** `new BigDecimal("10.0").equals(new BigDecimal("10.00"))` vaut `false` (l'échelle diffère). Utilisez `a.compareTo(b) == 0` (ou `isEqualByComparingTo` avec AssertJ).
3. **Division :** précisez toujours l'arrondi — `a.divide(b, 2, RoundingMode.HALF_UP)` — sinon `1 / 3` lève `ArithmeticException`.
:::

### En base de données vs calculs en mémoire

- **Colonne en base de données :** utilisez `BigDecimal` avec **`@Column(precision = 10, scale = 2)`** et une colonne SQL **`NUMERIC(10, 2)`** *(environ **1,5× à 2× plus volumineux** sur disque que `DOUBLE PRECISION` pour un prix courant — surcoût négligeable sur une table de quelques centaines de milliers de lignes)*. Associer `BigDecimal` en Java à une colonne SQL `DOUBLE` / `FLOAT` perdrait l'exactitude dès l'écriture en base.
- **Calculs en mémoire à partir de données en base :**
  - Si les colonnes sources sont en `NUMERIC` (`BigDecimal`), les calculs en mémoire restent exacts de bout en bout (total de ligne, TVA, remises).
  - Si la source en base est déjà en `DOUBLE`, passer par `BigDecimal` en Java ne corrige pas l'imprécision stockée en base, même si cela évite d'en ajouter pendant les arrondis.
  - Pour des **agrégations** (`SUM`, `AVG`) sur des centaines de milliers de lignes, calculez directement en SQL sur la colonne `NUMERIC` plutôt que de charger toutes les entités pour additionner en mémoire Java.

### Quel type choisir selon le besoin ?

- **`BigDecimal` + `NUMERIC` *(recommandé pour la finance)* :** prix, commandes, factures, TVA, remises, taux — dès que l'exactitude au centime et les règles d'arrondi comptent.
- **`Long` en centimes *(alternative performante)* :** stocker `1999L` pour `19,99 €` donne des calculs exacts sans coût `BigDecimal`. En contrepartie, toute l'équipe doit respecter la convention (centimes vs euros), convertir pour l'affichage/API, et attention aux devises n'ayant pas 2 décimales ou aux calculs de TVA.
- **`Double` + `DOUBLE PRECISION` :** mesures physiques, statistiques, coordonnées GPS, moyennes — dès qu'une précision approximative suffit *(ou pour simplifier un exemple pédagogique comme `Vin.prix`)*.

## Relations entre entités (`@ManyToOne` / `@OneToMany`)

Pour relier deux tables (ex. plusieurs `Vin` appartiennent à une `Region`) :

```java
@Entity
public class Vin {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Côté qui porte la clé étrangère (colonne region_id dans la table vin)
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "region_id")
    private Region region;
}

@Entity
public class Region {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Côté inverse (facultatif) : mappedBy pointe vers l'attribut Java "region" dans Vin
    @OneToMany(mappedBy = "region")
    private List<Vin> vins = new ArrayList<>();
}
```

- **Propriétaire de la relation (`@ManyToOne` + `@JoinColumn`) :** c'est l'entité qui porte la colonne de clé étrangère en base (`region_id`). Passez **`FetchType.LAZY`** explicitement sur `@ManyToOne` / `@OneToOne` (qui sont `EAGER` par défaut) pour ne charger la relation qu'à la demande.
- **Côté inverse (`@OneToMany(mappedBy = ...)`) :** déjà `LAZY` par défaut. Indique à Hibernate que la clé étrangère est déjà gérée par `Vin.region` (sans cela, JPA créerait une table de jointure inutile).
- **Optimisation et JSON :** l'optimisation des chargements (`N+1 SELECT`, `@EntityGraph`) est détaillée dans la page suivante [Spring Data JPA](/formation-api-rest/acces-donnees/spring-data-jpa/#optimisation-des-relations--le-problème-du-n1-select), et l'utilisation de DTOs pour éviter boucles JSON et `LazyInitializationException` dans [Contrats d'API](/formation-api-rest/api-rest/contrats-api/).

:::tip[Faut-il toujours déclarer le `@OneToMany` dans `Region` ?]
Non — une relation unidirectionnelle (`@ManyToOne` sur `Vin` uniquement) suffit dans la majorité des cas :

- **Avec `@OneToMany List<Vin> vins` :** appeler `region.getVins()` déclenche **2 requêtes SQL** pour une région (`SELECT ... FROM region WHERE id = ?`, puis `SELECT ... FROM vin WHERE region_id = ?`) — et **1 + N requêtes** sur une liste de régions — tout en obligeant à maintenir les deux côtés en Java (`vin.setRegion(r)` et `r.getVins().add(vin)`).
- **Sans `@OneToMany` :** déclarez une *Query Method* dans `VinRepository` et appelez-la depuis votre `@Service` pour renvoyer directement les vins au contrôleur (ex. `GET /regions/{id}/vins` ou `GET /vins?regionId=...`, convertis en DTOs). Hibernate n'exécute qu'**une seule requête SQL** (`SELECT ... FROM vin WHERE region_id = ?`), sans charger `region` ni alourdir la classe `Region` :
  ```java title="VinRepository.java"
  public interface VinRepository extends JpaRepository<Vin, Long> {
      List<Vin> findByRegionId(Long regionId);
  }
  ```
:::

## Génération du schéma (`ddl-auto`)

La propriété `spring.jpa.hibernate.ddl-auto` pilote ce que fait Hibernate au démarrage vis-à-vis des tables en base :

| Valeur | Comportement | Quand l'utiliser ? |
| :--- | :--- | :--- |
| **`none`** | Hibernate ne crée ni ne modifie aucune table | Quand les tables existent déjà en base ou sont créées par un script SQL (`schema.sql`) — **valeur par défaut** sur une base externe (PostgreSQL) |
| **`validate`** | Vérifie au démarrage que les tables et colonnes correspondent aux `@Entity` (sinon l'application refuse de démarrer) | Utile pour vérifier que la base et les entités Java restent alignées *(attention : strict sur les types SQL, ex. `Double` vs `NUMERIC`)* |
| **`update`** | Crée/ajoute les tables et colonnes manquantes d'après les `@Entity` | Prototypage uniquement *(à éviter en prod : ne supprime rien et ne gère pas les renommages/migrations complexes)* |
| **`create`** | Supprime puis recrée les tables au démarrage | Environnement jetable *(efface toutes les données à chaque redémarrage)* |
| **`create-drop`** | Comme `create`, puis supprime les tables à l'arrêt de l'application | **Valeur par défaut sur une base embarquée (H2)** si `ddl-auto` est omis *(d'où l'ajout de `none` dans `application.properties` pour utiliser `schema.sql`)* |

## Utiliser un autre schéma que `public`

Par défaut, les tables de l'application vivent dans le schéma **`public`** (recommandation actuelle sur les versions récentes de PostgreSQL pour une base dédiée à l'application). Si votre projet est branché sur un schéma dédié (ex. `mon_schema`) :

- **Réglage global (recommandé) :** ajoutez `spring.jpa.properties.hibernate.default_schema=mon_schema` dans `application.properties` *(s'applique à toutes les entités sans toucher au code Java)*.
- **Réglage ciblé (multi-schémas) :** précisez `@Table(name = "vin", schema = "mon_schema")` sur l'entité concernée.

:::caution[SQL natif et JDBC : `default_schema` ne s'applique pas]
`spring.jpa.properties.hibernate.default_schema` ne s'applique qu'aux entités JPA/Hibernate. Si vous utilisez un autre schéma que `public`, préfixez explicitement le nom de table (`FROM mon_schema.vin`) dans vos scripts `schema.sql`/`data.sql`, vos requêtes `@Query(nativeQuery = true)` et vos appels `JdbcClient` / `JdbcTemplate`.
:::
